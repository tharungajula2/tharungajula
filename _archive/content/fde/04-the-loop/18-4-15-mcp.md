## § 4.15 — MCP

Before USB-C, every device had its own charger — a drawer full of incompatible cables. One standard replaced the drawer.

**The problem MCP solves: the M×N explosion.** M applications each needing N tools means M×N bespoke integrations — every app re-implementing the same access, slightly differently, none reusable. MCP collapses this to **M+N**: each tool is wrapped *once* as a **server**; each application implements the **client** once; any client talks to any server.

That's the economic logic of every successful protocol. Standardise the interface and the integration count goes from multiplicative to additive.

**Three roles.** *Host* — the application the user interacts with. *Client* — the connector inside the host, one per server connection. *Server* — the wrapper exposing a specific capability.

Critically, **servers are reusable across hosts.** Write one once and any future MCP client can use it unchanged.

**Three primitives.** *Tools* — functions the model can call. *Resources* — data the client can read, read-only. *Prompts* — reusable templates the server offers. Most people meet MCP as "standardised tools" and stop; resources and prompts are the underused depth.

**Transport.** JSON-RPC 2.0 messages over either *stdio* — the server is a subprocess, client and server talk over standard in and out, the local default — or HTTP-based transports for remote servers.

Nothing magic. Structured messages over a pipe or a socket.

**THE DEPLOYMENT LENS.** MCP is genuinely useful at Meridian and genuinely dangerous, and the split is clean.

**Useful:** wrapping *their* systems. The loan origination system, the document store, the bureau interface. Wrap each once as an MCP server and every future AI tool Meridian builds can use them without re-integration. **That's an argument you can make to their platform team that has nothing to do with your project**, and it converts a one-off deployment into infrastructure — which is exactly how a pilot becomes a programme.

**Dangerous:** connecting your agent to third-party MCP servers. Which is § 4.16.

**And here's the FDE move.** When you propose wrapping their systems as MCP servers, you're proposing that Meridian build something that outlives your engagement and works with tools you didn't write. That's a genuinely generous architecture, and generous architecture is how you get invited back.
