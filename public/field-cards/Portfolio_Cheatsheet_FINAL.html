I built an end-to-end retail credit-risk system on 466,285 public LendingClub loans: a PD scorecard, two-stage LGD, EAD and expected loss, then IFRS 9 / Ind AS 109-style staging and ECL, Basel IRB capital, validation, stability monitoring and an automated reporting layer.
60–90 second versionthen stop
I started with the public 2007–2014 LendingClub loan book and created a 12-month default target, then split older vintages into development data and held the 2014 vintage out of time. For PD I used WoE/IV binning and logistic regression, then scaled the model into a scorecard and rating grades. I validated discrimination, calibration and stability using AUROC, Gini, KS, Hosmer–Lemeshow, PSI and CSI. For loss severity I used a two-stage hurdle LGD model: first whether any recovery occurs, then how much recovery occurs. EAD was outstanding principal at default for the term-loan book. I then combined the risk parameters into expected loss, built a 60-month lifetime PD term structure, implemented project-specific Stage 1/2/3 logic and ECL, and separately computed Basel III Advanced IRB RWA with a downturn-LGD stress. Finally I added portfolio monitoring and automated reporting. The important boundary is that the dataset is public US consumer data, so the framework transfers, not the raw calibration.

Bank customer churn

60-second answersay
I used a 10,000-customer churn dataset for binary classification. Because only about 20% churned, accuracy alone was misleading — predicting everyone stays already gets roughly 80%. I built small feed-forward neural networks, compared SGD and Adam, added dropout and hyperparameter tuning, then applied SMOTE only to the training set. The final SMOTE model moved churn recall from 0.48 on the baseline network to 0.75, with precision falling to 0.51. I accepted that trade-off because the business framing was low-cost retention outreach where missing a real churner mattered more than making an extra call.

Forecasting · chronology · seasonality

Antidiabetic prescription forecasting

A clean classical time-series workflow: see the structure, make it stationary, select SARIMA, test residuals, then prove it beats a simple seasonal baseline.

60-second answersay
The series had a rising trend and clear annual seasonality, so I treated it as a univariate time-series problem rather than randomly splitting rows. ADF testing showed the raw series was non-stationary; one ordinary difference was still insufficient, and adding a seasonal difference at lag 12 made it stationary. I then searched 625 SARIMA order combinations using AIC and selected SARIMA(2,1,3)(1,1,3)12. Residual diagnostics and Ljung–Box suggested no material autocorrelation remained. On a chronological 36-month holdout with rolling 12-month forecasts, SARIMA produced 7.90% MAPE versus 12.69% for the seasonal-naive baseline.

NIFTY 100 portfolio study

Not a prediction model: the question is how to combine assets so the portfolio earns a better return for the risk it takes.

60-second answersay
I started from the NIFTY 100 universe, downloaded adjusted prices and ended with 82 stocks with aligned usable history. I converted prices to log returns, annualised mean returns and the covariance matrix, then used an equal-weight portfolio as the baseline. I simulated 10,000 long-only fully invested weight vectors and computed expected return, volatility and a simplified Sharpe-style return-over-volatility score. The best simulated portfolio had about 15.27% expected return, 19.81% volatility and a 0.7707 score. The key concept is covariance: portfolio risk depends on how assets move together, not just each stock's individual volatility.

Part 05 · product concept

LOC-IQ: location intelligence as a graph.

A product/system story, not a trained credit-risk model. The strength is the reasoning architecture and interactive console; the boundaries matter just as much.

30-second versionsay
LOC-IQ is a Next.js concept console for location intelligence in credit underwriting and fraud review. It maps six applicant identifiers to a catalogue of 46 external data sources and 42 data fields, then visualises derived evidence in a six-layer directed graph. Demonstration scenarios apply composite weights — including a proxy-IP penalty — to rank candidate pincodes and show a location truth flag. The console and graph logic are real; the API responses and final scenario traces are illustrative static data rather than live integrations or a calibrated ML model.

Core distinction

Workflow when the path is known. Agent when it must choose.

Workflow

The developer writes the path. Example: upload → parse → validate → calculate → render. Predictable and easier to test.

Agent

The model chooses the next action from allowed tools and current state. More flexible, but every action needs stronger limits and traces.

Security boundary: the model can propose an action; application code decides whether that action is actually permitted to happen.

“How do you build with AI?”safe answer
I use AI heavily as a development accelerator, but I still own the problem framing, system structure, requirements, evaluation and the final output. I treat the model as one component inside an application: the app controls context, tools, state and permissions, and I keep known test cases so I can see whether a change helped or broke something. I can explain the files and logic I ship; bare live coding without assistance is a weaker filter for me than decomposition, domain reasoning and building the complete working system.
