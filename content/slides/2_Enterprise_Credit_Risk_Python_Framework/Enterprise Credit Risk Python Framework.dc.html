My Pydantic Schema Validation Engine

In plain Python a missing key or an "N/A" where a float belongs crashes in production with a TypeError. Pydantic is my automated security checkpoint: every variable is verified for type, range and format before execution proceeds.

from pydantic import BaseModel, Field, field_validator
from typing import List, Optional

class TradeLine(BaseModel):
    account_type: str = Field(..., description="Indian Bureau Account Type Code")
    sanction_amount: float = Field(..., ge=0, description="Sanctioned loan amount in INR")
    current_balance: float = Field(..., ge=0, description="Current outstanding balance in INR")
    amount_overdue: float = Field(default=0.0, ge=0, description="Overdue balance in INR")
    dpd_status: str = Field(..., description="Payment history string or current DPD status")

class BureauPayload(BaseModel):
    pan_number: str = Field(..., pattern=r"^[A-Z]{5}[0-9]{4}[A-Z]{1}$",
                            description="Indian PAN Card Number")
    cibil_score: int = Field(..., ge=-1, le=900,
                            description="CIBIL score, or -1 / 0 sentinel")
    trade_lines: List[TradeLine]
    total_inquiries_last_6m: int = Field(default=0, ge=0)

    @field_validator("cibil_score")
    @classmethod
    def validate_cibil(cls, v: int) -> int:
        # -1 = New-To-Credit, 0 = Insufficient History — valid sentinels
        if v in (-1, 0):
            return v
        if not (300 <= v <= 900):
            raise ValueError("CIBIL must be 300-900, or -1 (NTC) / 0 (Insufficient History)")
        return v

Target Engineering & the RBI 90+ DPD Rule

DPD · DAYS PAST DUE

The exact number of days elapsed since an EMI fell due and stayed unpaid.

RBI 90+ DPD → NPA

Any account unpaid for 90 consecutive days or more is officially a Non-Performing Asset. That is the regulator's definition, so it is my label.

MY BINARY TARGET OVER A 12-MONTH PERFORMANCE WINDOW
$$Y = \begin{cases} 1 & \text{if the borrower reaches } \ge 90 \text{ DPD (or charged-off / default) within 12 months} \\ 0 & \text{if the borrower stays performing (0–29 DPD) throughout 12 months} \end{cases}$$
def engineer_credit_target(df: pd.DataFrame) -> pd.DataFrame:
    """Regulatory 12-month binary default target."""
    default_statuses = ['Charged Off', 'Default',
                        'Does not meet credit policy. Status:Charged Off']
    df['ever_default'] = df['loan_status'].isin(default_statuses).astype(int)

    # Step 2 — months from origination to last payment (both cols parsed '%b-%Y')
    # Calendar-month arithmetic — safe under pandas 3.0 / numpy 2.x
    df['months_to_last_payment'] = (
        (df['last_pymnt_dt'].dt.year - df['issue_dt'].dt.year) * 12
        + (df['last_pymnt_dt'].dt.month - df['issue_dt'].dt.month)
    )

    # Step 3 — default must fall INSIDE the 12-month window
    df['default_12m'] = np.where(
        (df['ever_default'] == 1) & (df['months_to_last_payment'] <= 12),
        1, 0)
    return df

def create_temporal_oot_split(df: pd.DataFrame, date_col: str, split_date: str):
    """Splits strictly on time bounds — zero future data leakage."""
    df[date_col] = pd.to_datetime(df[date_col], format='%b-%Y')

    dev_mask = df[date_col] <  pd.to_datetime(split_date)
    oot_mask = df[date_col] >= pd.to_datetime(split_date)

    return df[dev_mask].copy(), df[oot_mask].copy()

Weight of Evidence: Mathematical Foundations

Regulators mandate linear, interpretable models. Raw neural networks and deep XGBoost ensembles are black boxes I cannot explain to an audit committee, so I buy explainability with WOE binning instead of surrendering it to a tree.

WEIGHT OF EVIDENCE FOR BIN i
$$\text{WOE}_i = \ln \left( \frac{\text{Distribution of Goods}_i}{\text{Distribution of Bads}_i} \right) = \ln \left( \frac{N_{\text{Good},i} / N_{\text{Good, Total}}}{N_{\text{Bad},i} / N_{\text{Bad, Total}}} \right)$$
N_Good,inon-defaulters falling in bin i N_Bad,idefaulters falling in bin i Totalsportfolio-wide good and bad counts lnnatural log — puts the ratio on an additive, log-odds-compatible scale
WOE > 0Bin holds a higher concentration of good borrowers than the portfolio average. Positive impact on the score.
WOE < 0Bin is concentrated in defaulters. Negative impact on the score.
WOE = 0Bin risk matches the overall portfolio average — the bin carries no information.

Information Value & Threshold Actions

WOE scores a bin. Information Value scores the whole attribute by summing each bin's separation weighted by its own WOE, across all k bins.

INFORMATION VALUE OF AN ATTRIBUTE
$$\text{IV} = \sum_{i=1}^{k} \left( \frac{N_{\text{Good},i}}{N_{\text{Good, Total}}} - \frac{N_{\text{Bad},i}}{N_{\text{Bad, Total}}} \right) \times \text{WOE}_i$$

PART C · FEATURE ENGINEERING, WOE & MONOTONIC ENGINE 12 / 52

Monotonicity Constraints & Missing Value Handling

WHAT MONOTONIC BINNING MEANS

As an attribute increases, default risk must move steadily in one direction. It cannot jump up and down between adjacent bins.

Higher income → lower probability of default. A monotone decrease in risk, every bin, no exceptions.

THE NON-MONOTONIC FAILURE

If a bucket shows borrowers earning ₹50 lakh defaulting more than borrowers earning ₹5 lakh because of a small-sample anomaly, the bin set is non-monotonic. I force the constraint rather than ship an artefact I cannot explain to a credit committee.

HOW I ENFORCE IT
01Start from quantile bins via pd.qcut with duplicates='drop' 02Compute the bad rate per bin and test the ordering 03Merge any bin that breaks the trend into its neighbour 04Require a minimum 5% population per surviving bin 05Constrain the logistic coefficients to be positive on WOE
MISSING IS INFORMATION, NOT ABSENCE

A blank months_since_last_delinquency usually means the borrower has never been delinquent. Imputing the median would destroy exactly the signal I need, so NaN and the bureau sentinel -9999 get their own dedicated bin with their own WOE.

My WOETransformer: the Fit Engine

class WOETransformer:
    """WOE + IV engine. Edges frozen at fit; missing (-9999 / NaN) gets its own bin."""

    def __init__(self, num_bins: int = 5, alpha: float = 0.5):
        self.num_bins   = num_bins
        self.alpha      = alpha   # Laplace count smoothing
        self.bin_edges_ = {}      # frozen numeric edges, open tails
        self.woe_dict   = {}
        self.iv_dict    = {}

    def fit(self, df: pd.DataFrame, target_col: str, feature_cols: list):
        n_bad_total  = df[target_col].sum()
        n_good_total = len(df) - n_bad_total

        for col in feature_cols:
            if np.issubdtype(df[col].dtype, np.number):
                edges = np.unique(np.nanquantile(df[col], np.linspace(0, 1, self.num_bins + 1)))
                edges[0], edges[-1] = -np.inf, np.inf   # open tails absorb unseen extremes
                self.bin_edges_[col] = edges
                df_bin = pd.cut(df[col], bins=edges).astype(str)
            else:
                df_bin = df[col].fillna('MISSING').astype(str)

            grouped = df.groupby(df_bin)[target_col].agg(['count', 'sum'])
            grouped.columns = ['total', 'bads']
            grouped['goods'] = grouped['total'] - grouped['bads']

            # Laplace count smoothing (alpha = 0.5) — no zero cell, no infinite WOE
            k = len(grouped)
            grouped['prop_goods'] = (grouped['goods'] + self.alpha) / (n_good_total + self.alpha * k)
            grouped['prop_bads']  = (grouped['bads']  + self.alpha) / (n_bad_total  + self.alpha * k)

            grouped['woe'] = np.log(grouped['prop_goods'] / grouped['prop_bads'])
            grouped['iv']  = (grouped['prop_goods'] - grouped['prop_bads']) * grouped['woe']

            self.woe_dict[col] = grouped['woe'].to_dict()
            self.iv_dict[col]  = grouped['iv'].sum()
bin_edges_ · OPEN TAILS
Fit persists the numeric edges with −inf and +inf bounds, so an income above anything seen in training still lands in a real bin instead of NaN.
TWO BINNING PATHS
Numeric attributes go through quantile cuts; categoricals keep their levels with an explicit MISSING level.
STATE I KEEP
Two dictionaries — woe_dict and iv_dict — are the entire fitted artefact. That is what gets pickled and shipped into the container.

I version the pickle filename with the training vintage. A serving container must never load a WOE map whose bin edges it cannot trace.

My WOETransformer: the Transform Engine

Transform is the method that runs in production, on one applicant at a time, inside a 50 ms budget. It reads the fitted maps and never recomputes them.

    def transform(self, df: pd.DataFrame) -> pd.DataFrame:
        df_woe = df.copy()

        for col, woe_map in self.woe_dict.items():
            if col in self.bin_edges_:   # frozen edges from fit() — never refit
                df_bin = pd.cut(df[col],
                                bins=self.bin_edges_[col]).astype(str)
                df_woe[col + '_woe'] = df_bin.map(woe_map).fillna(0.0)
            else:
                df_woe[col + '_woe'] = (
                    df[col].fillna('MISSING').astype(str)
                           .map(woe_map).fillna(0.0)
                )
        return df_woe
THE TRAP I WATCH FOR IN THIS METHOD

Re-running pd.qcut at transform time re-derives bin edges from the incoming batch. On a single-row API request that is meaningless. So transform calls pd.cut against the bin_edges_ persisted at fit time, and the same applicant always lands in the same bin.

SUFFIX CONVENTION
Every output column is <name>_woe. The raw column survives beside it so audit can reproduce the mapping.
fillna(0.0)
An unseen category maps to WOE 0 — treated as portfolio-average risk. Neutral is the only safe default when a new employment type appears mid-quarter.
WHY WOE, NOT ONE-HOT
WOE collapses k levels into a single monotone numeric column. My design matrix stays small, the coefficients stay signed and readable, and multicollinearity across dummies disappears.
CONTRACT WITH THE NEXT STAGE
The logistic model consumes only _woe columns, in a fixed order stored in model_config.yaml. Column order drift is a silent scoring bug, so the order is data, not convention.

Logistic Regression for Credit Scoring

Once my features are WOE values, the probability of default comes from a linear model on the log-odds scale. Linear in log-odds is exactly why a scorecard can be printed as a points table.

THE LOG-ODDS EQUATION I FIT
$$\ln \left( \frac{PD}{1 - PD} \right) = \beta_0 + \beta_1 \cdot \text{WOE}_1 + \beta_2 \cdot \text{WOE}_2 + \dots + \beta_p \cdot \text{WOE}_p$$

POSITIVE COEFFICIENT CONSTRAINT

Score Scaling Derivation: Factor & Offset

No underwriter or customer can interpret a raw log-odds of −2.415. I scale log-odds into integer points with three regulatory parameters, and those three numbers are the entire contract between my model and the business.

TARGET SCORE · S₀
700
The anchor point of the scale
TARGET ODDS · Odds₀
20 : 1
Good-to-bad ratio at the anchor
POINTS TO DOUBLE ODDS · PDO
40
Every +40 points doubles the odds of being good
THE TWO CONSTANTS
$$\text{Factor} = \frac{PDO}{\ln(2)}, \qquad \text{Offset} = S_0 - \big(\text{Factor} \times \ln(\text{Odds}_0)\big)$$
MY NUMBERS, SUBSTITUTED
Factor = 40 / ln(2) = 40 / 0.693147 = 57.7078
ln(20) = 2.995732
Offset = 700 − (57.7078 × 2.995732) = 527.123

These two constants are fixed at design time and never re-derived at scoring time. They live in model_config.yaml so a recalibration is a config diff, not a code change.

WHY ln(2) APPEARS

PDO is defined as the points needed to double the odds. Doubling on a log scale is exactly ln(2), so the factor is simply how many points I want to pay per unit of log-odds.

WHY THE BUSINESS CARES

import numpy as np

class ScorecardScaler:
    """Scales logistic regression log-odds into CIBIL-style
    integer scorecard points."""

    def __init__(self, target_score: int = 600,
                       target_odds: float = 50.0,
                       pdo: int = 20):
        self.target_score = target_score
        self.target_odds  = target_odds
        self.pdo          = pdo

        self.factor = self.pdo / np.log(2)
        self.offset = self.target_score - (self.factor * np.log(self.target_odds))

    def log_odds_to_score(self, log_odds: np.ndarray) -> np.ndarray:
        raw_score = self.offset - (self.factor * log_odds)
        return np.clip(np.round(raw_score), 300, 850).astype(int)

LGD Dynamics & the Bimodal Distribution Problem

When a borrower defaults on a ₹10 lakh loan, the bank does not lose ₹10 lakh. Recovery teams sell collateral and collect partial payments, so loss given default is what survives recovery.

Massive spikes at exactly 0.0 — full recovery — and exactly 1.0 — zero recovery. The middle is thin.

WHY A SINGLE REGRESSION FAILS

Ordinary least squares fits the mean of a bimodal target and lands in the empty middle. It predicts 0.55 for an account that will resolve at either 0.0 or 1.0, and it happily predicts values outside [0, 1], which is not a fraction at all.

The Two-Stage Hurdle (Tobit) Architecture

I split one impossible question into two answerable ones: will anything be recovered at all, and if so, how much. Each half gets the model class suited to its own distribution.

STAGE 1 · LOGISTIC CLASSIFIER
$P(\text{Recovery} > 0)$

The hurdle itself. A binary model on "was anything ever recovered", which is exactly the question the point mass at LGD = 1.0 represents.

STAGE 2 · LIGHTGBM REGRESSOR
$E[\text{Recovery Fraction} \mid \text{Recovery} > 0]$

Trained only on accounts that cleared the hurdle. LightGBM captures the non-linear collateral and tenure interactions a linear model cannot.

FINAL EXPECTED LGD
$$\text{Final Expected LGD} = 1.0 - \Big[ P(\text{Recovery} > 0) \times \text{Predicted Recovery Fraction} \Big]$$
WHY THE PRODUCT WORKS

The expectation of a censored variable is the probability of clearing the hurdle times the conditional mean beyond it. Multiplying the two stages reproduces that identity exactly.

BOUNDED BY CONSTRUCTION

A probability in [0,1] times a fraction in [0,1] can never leave the unit interval, so my LGD can never be negative or above 100% — no post-hoc clipping needed.

FDE ENTERPRISE HACK

Stage 2 must be trained on the positive-recovery subset only. Training it on all defaults reintroduces the zeros the hurdle was built to remove, and the two stages then double-count the same mass.

from sklearn.linear_model import LogisticRegression
import lightgbm as lgb
import numpy as np

class TwoStageLGDModel:
    """Hurdle LGD: P(recovery>0) x E[recovery | recovery>0]."""

    def __init__(self):
        self.hurdle = LogisticRegression(max_iter=1000)
        self.severity = lgb.LGBMRegressor(
            objective='regression', n_estimators=400,
            learning_rate=0.05, num_leaves=31,
            min_child_samples=50,
        )

    def fit(self, X, recovery_rate):
        # Stage 1 target: did ANY recovery occur?
        any_recovery = (recovery_rate > 0).astype(int)
        self.hurdle.fit(X, any_recovery)

        # Stage 2 trains ONLY on the positive-recovery subset
        mask = any_recovery == 1
        self.severity.fit(X[mask], recovery_rate[mask])
        return self

    def predict_lgd(self, X) -> np.ndarray:
        p_recovery = self.hurdle.predict_proba(X)[:, 1]
        frac       = np.clip(self.severity.predict(X), 0.0, 1.0)
        expected_recovery = p_recovery * frac
        return np.clip(1.0 - expected_recovery, 0.0, 1.0)

import numpy as np

def calculate_ifrs9_ecl(stage: int, hazard: np.ndarray, lgd: float,
                        ead_schedule: np.ndarray, eir: float,
                        remaining_life: int) -> dict:
    """IndAS 109 ECL. Stage 1 -> 12m; Stage 2 -> lifetime;
    Stage 3 -> lifetime with PD forced to 1.0 (default occurred)."""
    horizon = 12 if stage == 1 else remaining_life
    h = hazard[:horizon]

    # Survival to the start of each month, then marginal PD
    survival = np.cumprod(1.0 - h)
    survival_prev = np.concatenate(([1.0], survival[:-1]))
    pd_marginal = survival_prev * h

    if stage == 3:
        # Credit-impaired: default is certain, loss is LGD x EAD
        pd_marginal = np.zeros(horizon)
        pd_marginal[0] = 1.0

    months = np.arange(1, horizon + 1)
    discount = 1.0 / np.power(1.0 + eir, months / 12.0)

    ecl_vector = pd_marginal * lgd * ead_schedule[:horizon] * discount

    return {
        "stage": stage,
        "horizon_months": int(horizon),
        "pd_cumulative": float(pd_marginal.sum()),
        "ecl_amount": float(ecl_vector.sum()),
        "ecl_coverage_pct": float(ecl_vector.sum() / ead_schedule[0] * 100.0),
    }

My Discrimination & PSI Calculation Engine

import numpy as np
from sklearn.metrics import roc_auc_score
from scipy.stats import ks_2samp

def discrimination_metrics(y_true: np.ndarray, score: np.ndarray) -> dict:
    """AUC, Gini and K-S on a credit score (higher score = lower risk)."""
    auc  = roc_auc_score(y_true, -score)      # negate: score is inverse of risk
    gini = 2.0 * auc - 1.0
    ks   = ks_2samp(score[y_true == 0], score[y_true == 1]).statistic
    return {"auc": round(auc, 4), "gini": round(gini, 4),
            "ks_pct": round(ks * 100.0, 2)}

def calculate_psi(expected: np.ndarray, actual: np.ndarray,
                  n_bins: int = 10, eps: float = 1e-4) -> dict:
    """PSI with bin edges FROZEN on the baseline distribution."""
    edges = np.percentile(expected, np.linspace(0, 100, n_bins + 1))
    edges[0], edges[-1] = -np.inf, np.inf

    exp_pct = np.histogram(expected, bins=edges)[0] / len(expected)
    act_pct = np.histogram(actual,   bins=edges)[0] / len(actual)

    exp_pct = np.where(exp_pct == 0, eps, exp_pct)
    act_pct = np.where(act_pct == 0, eps, act_pct)

    contrib = (act_pct - exp_pct) * np.log(act_pct / exp_pct)
    psi = float(contrib.sum())

    verdict = ("HEALTHY" if psi < 0.10
               else "WARNING_RECALIBRATE" if psi <= 0.25
               else "CRITICAL_RETRAIN")
    return {"psi": round(psi, 4), "verdict": verdict,
            "bin_contributions": contrib.round(5).tolist()}
THE NEGATION
My score rises as risk falls, so roc_auc_score gets −score. Forget this and I report an AUC of 0.28 and panic over a good model.

Opening the outer bins to ±inf means new extreme scores are counted rather than dropped, so the percentages still sum to one.
eps = 1e-4

Discrimination and drift say nothing about level. Each quarter I run Hosmer–Lemeshow across score deciles — predicted against realised bad rate, chi-square on 8 degrees of freedom — and refit a Platt logistic on the raw score when it fails. Platt shifts the PD curve; the ranking, the WOE bins and the coefficients stay untouched.

Centralized Caching for CIBIL Payload Reuse

Every bureau pull is a paid API call and a network round trip of 200–800 ms — far larger than my entire scoring budget. An applicant who retries, edits the amount, or is re-scored by an underwriter should not trigger a second pull.

import redis, json, hashlib

CACHE = redis.Redis(host="10.0.0.3", port=6379,
                    socket_timeout=0.05, decode_responses=True)

BUREAU_TTL_SECONDS = 24 * 3600      # 24h freshness window

def _key(pan: str) -> str:
    return "bureau:" + hashlib.sha256(pan.encode()).hexdigest()

def get_bureau_payload(pan: str) -> BureauPayload:
    key = _key(pan)
    try:
        cached = CACHE.get(key)
        if cached:
            return BureauPayload(**json.loads(cached))   # ~2 ms
    except redis.RedisError:
        pass                                    # cache down != request down

    payload = cibil_client.fetch(pan)           # 200-800 ms, billed
    try:
        CACHE.setex(key, BUREAU_TTL_SECONDS, payload.json())
    except redis.RedisError:
        pass
    return payload

                                  k: int = 4) -> list:
